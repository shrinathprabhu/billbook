# Deploy Billbook to Cloudflare Workers

Billbook runs on **Cloudflare Workers Static Assets** at **https://billbook.lowkey.tools/**. The deployed package contains pre-rendered HTML, CSS, JavaScript, fonts, images and browser service workers. Documents, imports, taxes and exports still run entirely in the browser. No application Worker script, runtime SSR, database or runtime secrets are required.

Keep the trailing slash in the homepage canonical, Open Graph URL, JSON-LD, sitemap and HTTP canonical headers. Root-relative assets, manifest scope and browser service-worker scope remain `/`. No base path, parent-site proxy or cross-domain redirect is needed.

## Workers build settings

Connect [shrinathprabhu/billbook](https://github.com/shrinathprabhu/billbook) to the **billbook Worker** and use:

| Setting | Value |
| --- | --- |
| Root directory | Repository root (leave blank) |
| Build command | `npm run build` |
| Deploy command | `npm run deploy:workers` |
| Non-production branch deploy command | `npx wrangler versions upload --config deploy/cloudflare-workers/wrangler.jsonc` |
| Build environment variable | `NODE_VERSION=22` |
| Production branch | The branch you want to publish |
| Custom domain | `billbook.lowkey.tools` |

`deploy:workers` runs `wrangler deploy --config deploy/cloudflare-workers/wrangler.jsonc`. That checked-in config publishes `dist/workers`, declares the custom domain, enables Workers preview URLs, and sets explicit HTML and 404 handling. There is no separate output-directory field to configure in Workers Builds: `assets.directory` specifies it. Change `name` if the existing Worker has a different name.

The nested config lets Vinext generate the static HTML without treating the app as a runtime SSR Worker. The completed build also writes Wrangler's generated-config pointer at `.wrangler/deploy/config.json`, so a plain `wrangler deploy` after the build selects this same config and `dist/workers`. This replaces any pointer generated by Cloudflare's Vite plugin to intermediate output. The explicit commands above also work before that pointer exists. Do not add a second root Wrangler config or run framework migration/init during deployment. No custom `build.command` is set in Wrangler; Workers Builds runs the build once before deployment.

See Cloudflare's [Workers Builds settings](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/), [Static Assets configuration](https://developers.cloudflare.com/workers/static-assets/binding/) and [custom domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).

## Local build, preview and deployment

```sh
npm ci
npm run build
npm run test:build
npm run test:discovery
npm run test:workers
npm run preview:workers
```

The production preview runs through the Workers runtime at `http://127.0.0.1:8788/`. In another terminal, run `npm run test:workers:runtime` to verify actual HTTP responses, all offline assets, CSP and other headers, redirects, and 404/405 behavior. `npm start` and `npm run preview` use the same preview command. `npm run dev` remains the Vinext development server.

Wrangler's local proxy rewrites URLs matching the configured custom domain inside response headers, including the canonical `Link`, to the local preview address. The generated `_headers` file and HTML metadata retain `https://billbook.lowkey.tools/`; the artifact tests check that production value separately.

To validate deployment packaging without uploading:

```sh
npm run deploy:workers -- --dry-run
```

For a manual deployment, authenticate with `npx wrangler login`, then run `npm run deploy` to build and publish, or `npm run deploy:workers` to publish an already completed build. CI credentials such as `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are deployment credentials, never frontend environment variables. A local build, preview or dry run does not publish anything or change DNS.

The configured custom domain requires access to the `lowkey.tools` Cloudflare zone. Remove any conflicting previous domain attachment before assigning it to this Worker. Preview and `workers.dev` URLs retain the production canonical and have their own browser storage. The canonical is fixed in `lib/site.mjs` and never derived from the build host.

## Static output, headers and routing

`scripts/build-offline.mjs` prepares the static app. `scripts/build-workers.mjs` packages it into `dist/workers`, generates `_headers` from `scripts/security.mjs`, places the full CSP in both HTML documents, and versions the browser service workers against the final assets and header policy. Only `dist/workers` is uploaded. `dist/client` and `dist/server` are intermediate build directories.

Both packaging steps use `scripts/static-assets.mjs` to separate public assets from generated deployment files. Cloudflare's Vite plugin can emit `.assetsignore`, `wrangler.json` and `.dev.vars`; Vinext can add `_headers`. These files are excluded from the offline cache and final asset copy, along with other known build metadata. Billbook generates its own final `_headers`. Unexpected private or server files still stop the build with their paths listed, without logging their contents.

Workers Static Assets [limits each `_headers` line to 2,000 characters](https://developers.cloudflare.com/workers/static-assets/headers/). The full script-hash CSP exceeds that limit, so its document policy is placed immediately after the HTML charset, before resources and scripts. `frame-ancestors` stays in an HTTP header because [CSP meta cannot enforce it](https://www.w3.org/TR/CSP/#meta-element). Frame protection, HSTS, referrer, cross-origin and permissions policies also remain HTTP headers. `_headers` is deployment configuration and is excluded from the browser offline cache and public asset responses.

`assets.html_handling: "auto-trailing-slash"` normalizes `/index.html` to `/` with a 307 redirect. `assets.not_found_handling: "404-page"` serves the generated `404.html` with HTTP 404 for unknown URLs. Billbook uses a single root workspace; unknown paths never fall back to its app shell. Source maps and private/server files are excluded. These behaviors use the native Workers asset runtime; there is no application Worker handler. See [HTML handling](https://developers.cloudflare.com/workers/static-assets/routing/advanced/html-handling/) and [custom 404 pages](https://developers.cloudflare.com/workers/static-assets/routing/static-site-generation/).

Keep features that inject or rewrite JavaScript disabled, including automatic Web Analytics injection, Zaraz and Rocket Loader. The CSP permits the app's own scripts and local export resources.

## Build troubleshooting

`app/globals.css` deliberately uses `@import 'tailwindcss/index.css'`. Vite 8 can externalize the bare `tailwindcss` package during server build analysis and then try to read `/repo/tailwindcss` as a file. The explicit exported CSS path avoids this [Vite resolver bug](https://github.com/vitejs/vite/issues/23096). `npm run test:build` compiles the real stylesheet using default server externalization so this failure remains covered.

The packaging regression tests in the same command also run both packaging scripts with Cloudflare-generated files present. They verify that deployment metadata never enters public assets or the offline cache, that Billbook's headers and deploy pointer are generated, and that unexpected private or server files still fail safely. This covers the former `Unexpected private, server or Workers Static Assets control file` failure after a successful Vinext build.

## Install the PWA

Once deployed, open `https://billbook.lowkey.tools/`, wait for **Ready to work offline**, then choose **Install app**. Supporting browsers show a native install prompt; other browsers receive installation instructions. Use the custom domain for the regular workspace, since preview hosts have separate storage. The development server does not register the offline service worker.

## Search, answer engines and public files

Every build generates these root files:

- `/robots.txt` allows crawling and declares `https://billbook.lowkey.tools/sitemap.xml`.
- `/sitemap.xml` lists the subdomain homepage.
- `/llms.txt`, `/llms-full.txt` and `/index.md` describe public features, steps and FAQs.
- `/manifest.webmanifest` uses `/` for its ID, start URL and scope, with root-relative app icons.
- `/og.png` is the sharing card, with the credit `by @shrinath_prabhu`. Open Graph and Twitter metadata reference it on this subdomain.

The initial HTML includes the guide, use cases and FAQs without requiring JavaScript. The JSON-LD graph covers WebApplication, WebPage/FAQPage, Person, Organization and BreadcrumbList. Structured data and visible answers share the same facts in `lib/site.mjs`. The maker’s Person entity includes his X profile. Footer links credit Shrinath Prabhu, Owleye Analytics and Lowkey Tools, with one contextual recommendation for Credo.

Private bills, customer details, uploads and workspace data never become public HTML, sitemap entries or LLM documentation. These files support discovery; indexing and citations remain decisions made by search and answer engines.

## Security and caching

- Build-specific CSP SHA-256 hashes cover parsed inline scripts, hydration payloads and JSON-LD. Scripts have no `unsafe-inline` or `unsafe-eval` allowance.
- Inline styles support custom document design. Same-origin, `data:` and `blob:` images, fonts and export resources support local uploads and PDF/PNG generation. No analytics or external script dependency is enabled by the creator links.
- Frames, objects, form submissions and script attributes are blocked. Unused device permissions are disabled; clipboard write and native sharing remain available.
- Responses include HSTS, `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, COOP and CORP.
- Hashed static assets use a one-year immutable cache. HTML revalidates. Service workers are `no-store`; fixed-name images cache for one day, and discovery files/manifest for one hour. The error document is `noindex`; its explicit `/404` and `/404.html` header rules use `no-store`. Workers Static Assets controls caching for unknown URLs.
- Workers Static Assets handles unsupported methods and missing files with its native static responses as described above. Source maps, the internal client-entry manifest and known generated deployment files are excluded; the packager rejects unexpected private or server files in its input.

## Offline updates and existing data

New visits register `/sw.js` with `/` scope. The worker caches only known public app files and the homepage. It does not turn arbitrary unknown URLs into app pages or intercept requests to other origins.

A compatibility copy at `/standalone-sw.js` lets previously installed root workers fetch an update. It serves the same current worker; new visits use `/sw.js`. Activation cleans only Billbook’s own application-cache namespaces, including those used by previous versions. Updates wait for old app clients to close before activation, so editing is not interrupted by a forced reload. Neither the build nor the worker deletes IndexedDB documents, templates, settings or fonts.

Changing paths on the same origin preserves the workspace. Browser origins have separate storage: data previously created on the parent domain must be moved with the app’s JSON backup/restore. Do not clear site data to resolve a stale app cache or a previously cached redirect.

```sh
npm run lint
npm run typecheck
npm test
npm run test:build
npm run build
npm run test:discovery
npm run test:workers
npm run deploy:workers -- --dry-run
npm run preview:workers
# In another terminal:
npm run test:workers:runtime
```

After deployment, verify the live custom domain separately:

```sh
curl -I https://billbook.lowkey.tools/
curl -I https://billbook.lowkey.tools/sw.js
curl -I https://billbook.lowkey.tools/og.png
curl -I https://billbook.lowkey.tools/not-a-page
curl https://billbook.lowkey.tools/robots.txt
curl https://billbook.lowkey.tools/sitemap.xml
curl https://billbook.lowkey.tools/llms.txt
```

Expect HTTP 200 without a `Location` header for the homepage and public assets, and 404 for an unknown page. Check local save/import/export, keyboard navigation and an offline reload. Submit the subdomain sitemap to search consoles after deployment. Runtime tests and dry runs validate local packaging; DNS, live deployment and search-console submission remain separate actions.
